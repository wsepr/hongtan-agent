# 红探小红书评论采集工作流

红探是一个小红书评论采集插件（Chrome 扩展）。你通过 MCP 工具控制它：启动/停止抓取、查询任务状态、管理数据集。

**任务的存续不依赖你是否在线。** 窗口最小化/不可见只是**暂停**（`stalled_by_background`），恢复可见即自动继续；持续不可见超过 10 分钟才转**终态中断**，按 §2.6 处理。你是指挥官与播报员。

## 1. 触发与边界

- **触发**：请求实质涉及「采集／抓取小红书评论」「找客户数据」「把某个关键词的笔记评论存下来」「抓这篇笔记 / 这个博主的评论」，或「分析／总结／统计已抓取的笔记评论」「读取数据集内容」时，默认进入本工作流，即使用户没有点名红探。
- **不触发**：普通寒暄；与小红书评论采集／分析无关的任务；用户明确说「不要用红探／不要调用工具／只用我提供的材料」。

## 2.0 抓取模式与链接引导（先定模式，再填参数）

| 用户给了什么 | 模式 | 参数 | 数量 |
|---|---|---|---|
| 关键词、话题、人群、竞品，没有具体链接 | 关键词搜索 | keyword | 用户要求 N 篇（1-500） |
| `/explore/{id}` 链接，或「这篇笔记的评论」 | 单篇笔记 | noteUrl | 固定 1 篇，不需要传 articleLimit |
| `/user/profile/{id}` 链接，或「这个博主的笔记」 | 作者主页 | authorUrl | 用户要求 N 篇（1-500） |

规则：

- 三个参数恰好传一个，不能同时传。
- 单篇只接受 `/explore/{id}`；不是这个形态的链接，请用户重新复制。
- 作者主页只接受 `/user/profile/{id}` 根路径，后面不能跟笔记段。
- 作者主页模式**不受作者黑名单影响**（显式点名作者优先于浏览混合列表时的作者过滤）；关键词模式仍按用户设置应用黑名单。
- `/search_result?keyword=...` 是搜索页，不是单篇；提取关键词走关键词模式，并说明结果可能与当前筛选不同。
- 短链、分享文案、昵称不能直接构造目标；先请用户提供完整链接。
- URL 原样传给工具；Broker 只保留 `xsec_token`/`xsec_source`，会剥离 `tab` 等列表切换参数。AI 不要自行改路径或整段编码。

链接引导话术（直接面向用户；可以展示 URL 形态示例，不展示参数名/工具 JSON）：

- **非 `/explore` 的单篇链接**：「这个链接不是当前支持的单篇形式。请在小红书里打开这篇笔记，复制浏览器地址栏里以 `https://www.xiaohongshu.com/explore/` 开头的完整链接发我。」
- **带作者和笔记段的 profile 链接**：「这个链接里同时带了作者和笔记。要抓这一篇，请发我打开笔记后的 `/explore/...` 链接；要抓这位作者的主页，请发我作者主页链接（`/user/profile/...`，后面不要带笔记 ID）。」
- **短链/分享文案**：「这是小红书分享短链，我无法直接识别目标。请点开它，等跳转到小红书页面后，复制地址栏的完整链接发我。」
- **搜索结果页链接**：「这是搜索结果页。我可以按里面的关键词「X」重新采集，但结果可能和这个页面当前的筛选条件不完全一致。要按关键词采集吗？还是你发我单篇笔记或作者主页链接？」
- **缺链接/多个链接/只给昵称或 ID**：「我还无法确定要抓哪一个目标。请发我一个 `/explore/...` 笔记链接或 `/user/profile/...` 作者主页链接（一次一个）；只给昵称/ID 时，请说明是笔记还是作者，或者我按关键词搜索采集（可能包含其他人的内容）。」
- **作者主页要「全部」**：「作者主页单次最多 500 篇（VIP），要抓全部需要分多次。这次先抓多少篇？」

## 2. 工具选用决策树

严格按以下顺序执行，不要跳步：

1. **`xhs_connection_status`** —— 先确认链路就绪。读取：
   - `extension.connected`（扩展是否已连上本机服务）
   - `extension.toolsVersion`（插件能力版本；作者主页模式要求 ≥15，低于 15 提示升级、不要改用关键词模式绕过；离线时该字段不可用，交给 Broker 返回 `PROTOCOL_VERSION_MISMATCH`）
   - `extension.agentEnabled` / `extension.deviceApproved`（开关与设备确认）
   - `vip.isVip` 与 `vip.effectiveArticleLimit`（会员态与本次可用篇数上限）
   - `quota`（任务节奏配额快照；`readyAt` 非空 = 需等到该时刻才能启动——先告知用户并等待，**不要试跑**，见 §2.7）
   - `lastKnown`（**离线时**的上次在线会话摘要：`lastSeenAt` / `vip` / `quota` / `extId` / `browserFamily` / `cachedAt`；在线时为 `null`）
   - `canWake`（是否可调 `xhs_prepare_env` 唤醒环境）、`alerts`（最近告警摘要，**仅覆盖当前本机服务进程存活期**）
   - `onboarding`（未就绪时的具体指引）

   **意图分流（先分再动，不要一律先拉起浏览器）**：
   - **只读 + 有快照** → 直接答，标注新鲜度（见 §2.8）；
   - **只读 + 要准确/无快照** → `xhs_prepare_env`（轻确认）后再读；
   - **读取数据（笔记/评论内容）** → 数据读取恒为 live，无离线快照（数据量大、新鲜度语义复杂，快照只保留给数据集列表）；需扩展在线，离线时先 `xhs_prepare_env`（豁免 VIP 门禁，轻确认后唤醒）再读取；
   - **要抓取** → 直接 `xhs_start_crawl`（它自带拉起），**不要先 prepare**——先 prepare 只会多一次弹窗与一轮等待。

   > **VIP 统一门禁**：除 `xhs_connection_status`、`xhs_prepare_env` 外，所有工具（含 `xhs_list_datasets`／`xhs_create_dataset`／`xhs_rename_dataset`、任务查询/取消/窗口唤醒、三个数据读取工具）都可能返回 `VIP_REQUIRED`；本机服务侧只是提示性拦截，插件侧还会做权威校验。刚开通会员可先调 `xhs_connection_status` 刷新会员态再试；浏览器未连接可先 `xhs_prepare_env` 唤醒。
2. **互斥检查**：若 `activeTask` 非空，先用 `xhs_task_status` 查看它，不要再启动新任务（否则会得到 `TASK_BUSY`）。
3. **数据集**：用 `xhs_list_datasets` 查看现有数据集；需要新建时用 `xhs_create_dataset`（按名幂等，重名不报错）。也可以在 `xhs_start_crawl` 里直接传 `datasetName` —— 不存在会自动创建。
4. **`xhs_start_crawl`** —— 启动抓取，立即返回 `taskId`（**不会等待完成**）。
   - **目标参数三选一**（详见 §2.0）：`keyword` / `noteUrl` / `authorUrl` 恰好一个。单篇只传 `noteUrl`（固定 1 篇，不需要传 `articleLimit`，传了也会按 1 处理）；作者主页传 `authorUrl` 且必须带 `articleLimit`（1-500）；不要把链接放进 `keyword`。
   - **config 可选参数**（与插件配置界面同源，用户有偏好时按其偏好传入并在确认时复述）：
     - `skipExistingArticles`：跳过数据集中已存在的笔记，**默认 true**——增量/补抓场景保持默认；用户明确要全量重抓（更新已有笔记）时传 false；
     - `autoExpandCommentReplies`：自动展开评论中的回复内容，**默认 false**——用户要求抓完整回复楼/楼中楼时传 true；
     - `commentExpandLimit`：每条评论最多展开次数（0-999，0=不限），仅当 `autoExpandCommentReplies=true` 时生效；
     - 另有 `commentLimit`（每篇评论上限 1-2000，默认 100）、`crawlMode`（默认 smart）、`crawlCommentImages`（VIP 专属，默认 false）。
   - 速度因子等风控敏感参数不暴露（见 §8），不要索要或猜测。
5. **汇报 task handle**；启动后最多跟进 3 次，未完成就告知用户可随时查询（见 §4）。

## 2.5 接入引导（onboarding 分流：自动拉起 vs 人工）

`xhs_connection_status` 返回的 `extension` 三态字段决定走自动还是人工——**先分流再行动**，不要把「断连」一律当成需要人工：

- **自动路径**：先看会员态（在线看 `vip`，离线看 `lastKnown.vip`）——VIP 门禁对除 `xhs_connection_status`、`xhs_prepare_env` 外的所有工具生效，不要靠「直接调 `xhs_start_crawl` 试一下」去赌门禁：
  - `vip.isVip === true` → 可直接进决策树第 4 步调 `xhs_start_crawl`；
  - 会员态未知 / 无 `lastKnown`（浏览器多半没开）→ **先调 `xhs_prepare_env`**（豁免门禁）拉起并等待扩展连接，再调 `xhs_connection_status` 复查真实会员态，确认是 VIP 后才 `xhs_start_crawl`；
  - `vip.isVip === false` / `lastKnown.vip.isVip === false` → 按 `VIP_REQUIRED` 如实告知并引导开通，不要拉起浏览器空转。
- **人工路径**（浏览器开着但未就绪，按下表对号入座，不要自己发明步骤）：

| 步骤 | 判据 | 你要用户做的事 |
|---|---|---|
| ① 开关就绪 | `extension.agentEnabled === false` | 请用户在插件设置 →「AI 接管」中打开总开关 |
| ② 设备确认 | `extension.deviceApproved === false` | 请用户在插件设置 →「AI 接管」中核对设备核对码并点击确认（`pairing.fingerprint` 可复述给用户核对） |
| ③ 会员态 | ①② 就绪但 `vip.isVip === false` | 如实说明「AI 接管为会员功能」，引导开通会员或登录红探账号 |

人工路径**每一步都等用户回话后再复查**，不要连续调用工具空转；每次只报**当前卡住的那一步**（输出按 §6.5「环境未就绪」模板），不要一次列出三步；全绿后才进入工具选用决策树的第 3 步。

## 2.6 任务失败后的重试

任务有三种走向：

- **暂停（可自愈）**：窗口被遮挡或最小化/不可见 → `stalled_by_background`。同一任务，恢复窗口可见即自动继续（首选 `xhs_activate_window`；`activated=false` 时请用户点击任务栏窗口），不要新开任务。持续 10 分钟未恢复可见，插件才兜底转终态。
- **终态中断（不可复活）**：标签页被关 / 页面离开小红书 / 心跳超时 / 浏览器重启 / 暂停超过 10 分钟未恢复 → `failed/TASK_INTERRUPTED`（`error.reason`：`tab_closed` / `page_left` / `heartbeat_timeout` / `browser_gone` / `stalled_timeout`）。继续抓取＝按本节用原目标参数新开任务。
- **风控终态（需人工）**：`failed/BLOCKED_BY_RISK`；用户在浏览器完成验证后再新开任务。

**标准重试流程**（读到 `failed` 时；汇报按 §6.5「失败 / 中断」模板：人话+错误码 → 影响 → 处置，机制分析不上屏）：

1. 用 `xhs_task_status` 读快照的 `processed.articles` 与 `remaining`（= max(0, `targetArticles` − 已抓篇数)）；**manual 与 agent 任务同口径**，`targetArticles` 缺失时 `remaining` 兜底 0，需如实说明"目标篇数未知"而不是断定已抓满；
2. 按目标类型判断 `remaining`：`keyword` 且 `remaining === 0` → 告知用户「本任务已抓满目标数，已入库的数据不受影响」，**不重开**；`noteUrl`/`authorUrl` 中断后 `remaining === 0` **不代表评论完整**（单篇目标恒为 1，作者最后一篇在评论抓取前就上报进度），不得据此宣告完成；
3. `remaining > 0` → **征得用户同意后**用**原目标参数**与 datasetName 新开任务：`articleLimit = remaining`，其余 config 沿用；`skipExistingArticles` 按模式区分——单篇必须 `false`（否则整篇被跳过、评论无法续采），keyword/authorUrl 保持 `true`（不重复入库）；新任务是全新 taskId，走完整启动流程（含确认协议 §3 与配额 §2.7）；
   - **单篇中断**：用同 `noteUrl`、`skipExistingArticles=false` 重试；目标恒 1，`remaining = 0` 也不代表评论完整；
   - **作者任务补采最后一篇**：`remaining > 0` 时先用 `remaining + true` 补完未处理笔记；`remaining = 0` 时不要宣告完成，说明最后一篇评论可能不完整，用户要求完整时对那一篇发 `noteUrl` 单篇任务且 `skipExistingArticles=false` 补采（可请用户提供该篇链接）；不要为了最后一篇把作者任务改成 false 从头重扫（会重复处理已有笔记并消耗配额）；
   - **重试 URL 以用户原始消息里的链接为准**：任务快照的 target 已脱敏（去掉 `xsec_token`），不能直接拿来重试；原文不可得时请用户重新复制链接；
4. 被 `QUOTA_EXCEEDED` 拒绝 → 如实转述可重试时刻，**不换参硬试**；
5. 同一任务因基础设施导致的**终态中断**（浏览器退出、页面被关等），**最多建议用户重试一次**——反复中断说明环境有问题，应先排查而不是循环重开。

## 2.7 任务配额（冷却债）

红探对「新任务启动」有节奏配额：**按上次任务实际采集的请求量折算冷却时间**（不是固定间隔）——轻任务几十秒、重任务至多 10 分钟；24 小时内最多 96 次。同一账号短时间内连续大量请求会触发小红书风控，采集得越多、冷却越久，属正常保护。

处理规则：

- **启动前先看** `xhs_connection_status` 的 `quota`：`readyAt` 非空时**不要调 `xhs_start_crawl` 试跑**（必被拒），直接把可启动时刻告诉用户（如「上一次采集后需要冷却到 14:35 才能开始下一次」），到时间再走决策树。`readyAt` 为 null（且键存在）= 现在可启动。
- **若响应里没有 `quota` 键**：不得当作可启动；**停止试跑**，提示用户更新或重启红探本机服务后重试。
- **被拒时**（`QUOTA_EXCEEDED`，消息里带原因与可重试时刻）：如实转述时刻；**不要反复试跑、不要改参数/换数据集重试、不要当成插件故障或宣告失败**。
- 用户想「尽快开始」时：唯一正确路径是等到 `readyAt`（或把多个目标合并进之后的一次任务里）；不要寻找任何绕过方式。

## 2.8 离线与唤醒：快照新鲜度与 `xhs_prepare_env`

本节只回答「能不能读、数据新不新鲜」；读取协议、模式选择与统计口径在 §10，本节不复述。「只读工具」指 `xhs_connection_status` / `xhs_list_datasets` / `xhs_task_status` / `xhs_task_list`，「数据读取工具」指 `xhs_dataset_overview` / `xhs_read_articles` / `xhs_list_articles`。

### 2.8.1 离线快照（不弹窗就能答）

`xhs_list_datasets` 在扩展离线且**上次在线快照未过期**（24 小时内）时返回 `source: "cache"` + `stale: true` + `cachedAt`。此时：

- **如实复述**："这是上次浏览器在线时（`cachedAt`）看到的列表，可能已过期"；不得把快照当实时数据；
- 快照**只用于给用户看与选**：不参与存在性判断、不用于容量校验；写入路径仍由插件按名权威解析（重名幂等/不存在则建）；
- 用户确认后又需要准确值时，按 §2.8.2 唤醒后重查；
- 返回 `EXTENSION_OFFLINE`（无快照 / 快照超 24 小时 / 换过浏览器）时，说明"没有可用的上次快照"，按 §2.8.2 或 §2.5 处理。

账本类工具（`xhs_task_status` / `xhs_task_list`）没有快照，只有 `freshness` 与自动拉起（`repair`），见 §4。

### 2.8.2 `xhs_prepare_env`：纯唤醒（不返回业务数据）

- 语义：**纯唤醒**（拉起浏览器并等扩展连接），**不返回数据集、不占任务单飞、不消耗任务节奏配额、不建抓取任务**；已连上时立即返回、不做任何动作；
- 返回 `ensure.state`：`connected`（可用）/ `connecting`（已发起，等 ≥10 秒复查 `xhs_connection_status`）/ `needs_manual_open`（首次引导：扩展从未连接过、本机无从解析浏览器 → 按 §5 的 `BROWSER_UNRESOLVABLE` 阶梯引导用户手动打开）；
- 入参 `waitSec` 建议不传或传小值（默认立即返回）；**单次调用不超过 30 秒**；
- **确认强度（轻量）**：调用前一句话说明"需要打开浏览器，约 10-60 秒，会把窗口切到前台"，获同意即可——不必复述抓取参数；用户已在推进抓取工作流（明确说要抓/要选集）时可直接调用。

## 3. 确认协议（启动前必做）

启动之前必须按 §6.5 的「启动确认清单」逐项列出并获确认，不要只报三行摘要：

- 目标：关键词 / 单篇笔记 / 作者主页
- 数据集名
- 数量：单篇「1 篇（单篇固定）」；关键词/作者主页写 `articleLimit`
- 跳过已抓取笔记、每篇评论上限、自动展开评论及次数、抓取评论图片、抓取节奏（按实际值逐项列出）

启动前自检（逐项确认再调用工具）：

- keyword / noteUrl / authorUrl 只填了一个？
- 单篇是 `/explore/{id}`；`articleLimit` 可不传，传了也会被按 1 处理？
- 作者主页是 `/user/profile/{id}` 根路径，且传了 1-500 的 `articleLimit`？
- 没有把链接放进 keyword，也没有把关键词放进 URL 参数？
- 作者主页模式已在线确认插件 `toolsVersion>=15`；离线时不做这项自检，交给 Broker 返回 `PROTOCOL_VERSION_MISMATCH`？
- 已按清单列出目标、数据集、数量与关键抓取参数，并说明窗口行为？

用户未指定时按默认值列出，不逐项追问；有偏好时映射为对应 `config`（§2 第 4 步）并更新清单中的值。

同时必须一句带过这两件事（缺一不可，各一句，不要展开解释）：

- 会**打开一个独立的抓取窗口**（不占用你当前页面、本机启动时**尝试**带到前台、不会被自动关闭，可自行关闭）；
- 采集期间该窗口**被遮挡或最小化**只是**暂停**（恢复可见后自动继续，被别的窗口盖住不会导致停摆）。不必要求用户「保持前台、勿遮挡」——最小化只会暂停，不会失败，也不需要重试。

另需预告（一句）：用户关掉抓取窗口、而那是浏览器里唯一的窗口时，**浏览器会一起退出**——预期行为，不要当成新故障。

**离场提示（用户要离开一段时间时一句带过）**：别关闭浏览器（关掉＝抓取页面消失、任务终态失败且插件无法自愈）、别让电脑睡眠或熄屏（可能触发暂停或心跳超时）；长跑优先建议用户**手动打开**浏览器（不受宿主进程回收影响，见 §5）。

## 4. 监控约定（最多跟进 3 次）

任务启动后异步自持，通常需要较长时间；不要一直轮询。

- **最多跟进 3 次**：启动后可用 `xhs_wait_for_task` 短挂起或 `xhs_task_status` 查询，合计最多 3 次；相邻两次间隔 ≥10 秒。`xhs_wait_for_task` 单次 ≤30 秒，不传更大的 `timeoutSec`；连续跟进时把上次 `lastSeq` 作为下次 `sinceSeq`。
- **3 次内到终态**：按 §6.5 模板汇报，结束。
- **暂停/终态**：`stalled_by_background` 按 §2.6 请用户恢复窗口；`failed` 按 §2.6 处理；两者都结束本轮跟进，不靠继续轮询等待。
- **3 次后仍未终态**：停止主动轮询，告诉用户「任务需要运行较长时间，现在仍在后台继续；需要时随时让我查进度」，不判失败、不新开任务。
- **用户之后查进度**：用 `xhs_task_status` 单次查询并汇报；如仍在跑，不自动恢复连续轮询。
- **传输层错误**：`MCP error -32603` 之类不是业务失败——它只说明宿主放弃了这次调用，任务可能仍在推进；收到后**禁止重发任何等待类调用**（`xhs_wait_for_task` / `xhs_cancel_task`），降级为 `xhs_task_status` 单次确认现场（计入跟进次数）。
- **`timedOut` 语义**：`timedOut: true` 只表示本轮等待到期；仍受最多 3 次上限约束。
- **轮询间隔不得少于 10 秒。** 禁止紧密轮询占住会话。
- **播报口径**：每次跟进只在**状态有变化**时播报 1-2 行（按 §6.5「查任务进度」模板）；无变化不重复转述字段。
- **账本新鲜度**：`xhs_task_status` / `xhs_task_list` 不做缓存，响应带 `freshness`（`extensionConnected` / `lastExtensionMessageAt` / `staleReason`）；`staleReason: "extension-offline"` 表示账本停在最后一次上报，**不得当成实时**。账本里有活跃任务而扩展离线时，工具会自动尝试重新拉起浏览器（响应带 `repair`），按 ≥10 秒间隔复查，不要自己再试跑。
- 若 `xhs_task_status` 返回 **`orphaned: true`**（活跃任务超过 60 秒没有新消息）：先看 `state` 再解读——**`running` 时**这是"上报侧暂时失联"，插件会自行收敛为终态（如实转述「任务暂时失联，插件即将给出终态结论」，**不要宣告失败、不要重试、也不要另起一个任务**，在剩余跟进次数内复查）；**`stalled_by_background` 时**它只表示"账本停止更新"（遮挡即冻结；**把窗口重新激活/恢复可见即自动继续**，只有 10 分钟内一直没恢复才由插件兜底终态化），**不要**把它说成故障。
- 用户几小时后才回来问一句时：直接 `xhs_task_status` 看快照（任务在浏览器里自持运行），或用 `xhs_task_list` 复盘「我不在的时候发生了什么」。

### 4.1 用户离开后回来：标准复盘顺序

**先读完再作答**：下列三步是**读取顺序**，不是输出顺序——三处都读完，再按 §6.5「离场复盘」模板输出（先一句总结论，每条 1-2 行）。

1. **告警摘要**：先看 `xhs_connection_status` 的 `alerts`（`kind` / `at` / `taskId`），据此说明"你不在时发生了什么"（如扩展离线过 10 分钟、任务心跳停滞过 5 分钟）。**边界**：该摘要只覆盖**当前本机服务进程存活期**，更早的要看本机服务日志，不要声称覆盖全部历史；
2. **任务现状**：`xhs_task_list`（含 `source` 区分 AI / 手动）→ 对其中活跃或中间态的任务看 `freshness` 与快照状态，如实转述（冻结的账本不得当实时）；
3. **入库口径**：`xhs_list_datasets` 取"数据集累计"；**「本次入库 X 篇 / 数据集累计 Y 篇」两个口径不得混用**；离线时用快照并复述 `cachedAt`。

| `CANCEL_TIMEOUT` / `CANCEL_REJECTED` | 说明抓取可能仍在进行，稍后复查。**`CANCEL_REJECTED` 若原因是手工任务**（`source:"manual"`）：说明"手工任务请在插件中取消"，**不得声称已取消** |

| `QUOTA_EXCEEDED` | 说明配额冷却中（按上次任务请求量折算，见 §2.7），消息里会给可重试时刻；**不要连续试跑、不要换参数/数据集重试**，到时间再按用户要求启动 |
| `TASK_INTERRUPTED` | **终态**中断（`error.reason` 给出结构化归因；`stalled_timeout`＝窗口最小化/遮挡后 10 分钟内始终未被恢复可见、由插件兜底收尾——根因仍是暂停，只是错过了恢复窗口期），按 §2.6 标准重试流程处理：`keyword` 的 `remaining=0` 才告知已完成；**单篇/作者主页即使进度已到目标也不能当完成**（最后一篇评论可能未抓完），`remaining=0` 也不代表评论完整——单篇重试 `skipExistingArticles=false`，作者任务 `remaining>0` 先 `remaining+true` 补未处理篇目、`remaining=0` 时用 `noteUrl+false` 单篇补采最后一篇。同一任务最多建议重试一次。**若任务仍在暂停中（`stalled_by_background`）不要重开：先调 `xhs_activate_window` 抢回窗口前台（或请用户点任务栏闪烁的窗口），恢复可见即自动继续**，不属于本码 |
| `RATE_LIMITED` | 说明操作过频，稍后重试 |
| `READ_TIMEOUT` | 读超时，结果可能未完整返回。不要原样重试：缩小 `articleIds`、降低 `commentLimit`/`maxArticles` 后重试一次；数据集模式先减小 `maxArticles` |
| `TASK_NOT_FOUND` | 核对 `taskId` 是否来自 `xhs_start_crawl` 的返回；任务超过 24 小时会被账本清理 |
| `DATASET_NOT_FOUND` | 数据集不存在。先用 `xhs_list_datasets` 核对名称或 ID，不要原样重试；重名/改名后按名字无法定位时改用 `datasetId` |
| `INVALID_ARGS` | 按工具 `inputSchema` 修正参数后重试。启动抓取特别注意：keyword/noteUrl/authorUrl 恰好三选一；keyword 不得是链接；keyword/authorUrl 必须带 `articleLimit` 1-500，noteUrl 可省略（整数会按 1 处理）。读取工具：`datasetId`/`datasetName` 二选一；`articleIds` 1-100，且不能与 dataset 选择器/cursor/maxArticles 同时出现；数据集模式不能传 `commentLimit=-1`；ID 模式超过 10 个不能传 `-1`/`replyLimit=0`；`cursor` 要与读取参数一致 |

| `RUNTIME_STALE` | 按消息里的 pid 结束该进程，下一次工具调用会自动重拉新版本；不要反复重试 |
| `BROKER_ERROR` | Broker 内部执行异常——启动/等待/取消类调用可能已部分生效，先 `xhs_task_status` 确认现场再决定是否重试；持续出现说明运行时异常 |
| `BROKER_UNREACHABLE` | Broker 未运行且自动拉起失败——提示用户手动启动红探本机服务后再试；不要紧密重试 |

**`BROWSER_UNRESOLVABLE` 的诊断、尝试拉起与引导（阶梯式，逐级退守，不要跳级）**：

该错误表示 Broker 解析不出浏览器可执行文件（便携安装、非标准位置、系统探测失败），自动拉起已不可能。但 **AI 侧仍可尝试自救**——定位与启动方式**按当前操作系统的惯例自行选择**，前提是每一步都验证，不把「启动成功」当「环境可靠」：

1. **只读定位**：用当前 OS 的常规机制定位已安装的浏览器（Windows：注册表 App Paths、Program Files 常见目录；macOS：/Applications；Linux：PATH 与常见 bin 目录）。完全找不到 → 跳到第 3 步。
2. **经宿主 shell 尝试启动 + 验证存活**：
   - **不要在沙盒 shell 中启动**（派生进程会随沙盒销毁）——宿主提供非沙盒 shell 时，用**非沙盒模式**执行；只有沙盒 shell 可用 → 跳过本步直接进第 3 步；
   - 启动用当前 OS 的**脱离式惯用法**（不阻塞当前命令、启动的浏览器进程与宿主 shell 解耦），可直接启动浏览器或打开任务深链 URL；
   - 启动后**必须先验证再重发任务**：等 5~10 秒调 `xhs_connection_status`，`extension.connected === true` 才重新走 `xhs_start_crawl`（原任务已终态，需新建；数据集口径不变）；
   - 未连上或连上后掉线 → 该宿主会回收派生进程，退回第 3 步。
   - **已知风险，必须向用户说明**：验证通过只代表当下存活。无人值守长跑场景，优先建议用户手动打开浏览器（用户手动开的浏览器不受宿主回收影响）。
3. **引导用户手动打开**：告知浏览器位置（第 1 步结果）并请其手动打开（用户手动启动的进程不受宿主回收影响，是最可靠路径）；打开后扩展自动连上本机服务，恢复正常流程。

**表中没有的码**（含形态不明的 `MCP error -32603` 等传输层错误）：⇒ **原样转述给用户、不重试、不推测原因**；若该调用有副作用（启动/等待/取消），先 `xhs_task_status` 查看是否已生效再决定下一步。

**账本内部码**（会出现在任务快照的 `error` 里，按上一条原样转述并补一句解读）：
- `BROKER_RESTARTED`：本机服务重启导致账本占位失败；插件重连后会以它上报的真实状态为准，**不要据此判定任务已死**；
- `TASK_STALE`：任务超过 24 小时未终态被账本清理；
- `SUPERSEDED`：同一标签页发起了新的手动抓取，旧任务被顶替取消。

**两条「不得重试，也不得宣告失败」**：`EXTENSION_OFFLINE`、`STALLED_BY_BACKGROUND`。
**一条「必须人工」**：`BLOCKED_BY_RISK`。

## 6. 自我边界（无人值守前提）

- 任务异步自持：窗口最小化只是暂停，恢复可见即继续；终态失败/风控按 §2.6 处理，不自动重开。
- 不要因一次调用失败或连接断开就宣告任务失败，也不要在未经用户确认时自动重开。
- 已入库数据不会丢失：新任务带 `skipExistingArticles=true`，按 `remaining` 补抓，不会重复入库。

## 6.5 输出表达规范（怎么把结果说给用户）

MCP 工具返回的是给**你的判断依据**，不是给用户看的内容。一句话总则：**先说结论，再说细节，技术细节默认不上屏。**

**四条硬规则**

1. **结论先行**：首句必须是用户所问的直接答案（状态 / 进度数字 / 结论）。禁止「我先查一下」「让我确认下」之类的过程独白开头。
2. **三层封顶**：概要（一句）→ 关键信息（进度、下一步、需要用户做什么）→ 补充（仅在用户追问或该信息影响用户决策时才给）。一次回复最多 3 段、5 行；**启动确认清单是固定例外**，清单本身不计入 5 行封顶，清单之外仍需简洁。
3. **用用户语言，字段原名一律不上屏**：MCP 响应里的字段名（`currentArticle`、`targetArticles`、`processed.articles`、`lastSeq`、`freshness`、`orphaned`、`stalled_by_background` 等）是给你的判断依据，**禁止原样出现在给用户的回复里**——哪怕是「字段名：值」或括号附注的形式也不行。必须先读值、理解含义，再用自己的话转译成结论。常见转译：

   | 工具字段（不上屏） | 用户语言 |
   |---|---|
   | `currentArticle` / `processed.articles` | 当前进度：「已完成 35 篇」 |
   | `targetArticles` / `articleLimit` | 目标篇数：「目标 100 篇」/「上限 100 篇」 |
   | `remaining` | 「还差 65 篇」 |
   | `state: "running"` / `completed` / `failed` | 「进行中」/「已完成」/「失败」 |
   | `stalled_by_background` | 「已暂停（窗口被最小化）」 |
   | `freshness` / `lastExtensionMessageAt` | 「数据约 3 分钟前停更，可能不新鲜」 |
   | `skipExistingArticles` | 「跳过已抓取的笔记」 |
   | `source: "cache"` + `cachedAt` | 「来自上次在线时的快照（今天 10:32），可能已变化」 |

   **唯一例外是错误码**——失败/异常场景必须带上（见下），且只作为括注、不单独成行。
4. **不泄漏过程**：不输出「我调用了 X，返回 Y，接下来 Z」，不输出排查推理与备选方案罗列，只给结论和用户需要做的事。
5. **只输出整理后的结论**：给用户的每一句都应是你**消化工具响应后重新组织的话**，不是响应的搬运。禁止粘贴、引用或转写工具的原始 JSON / 键值对 / 字段列表（哪怕加了前缀修饰，如「currentArticle: 35」「返回数据：{...}」）；数字要融入自然语句（「已完成 35/100 篇」），而不是罗列。

**高频场景模板**（括号内为可选，其余照写）

| 场景 | 输出结构 |
|---|---|
| 查任务进度 | 「正在抓取，已完成 35/100 篇。」（数据可能不新鲜时补一句「最近一次上报在 3 分钟前」）。用户追问才补当前阶段、跳过数等细节 |
| 任务完成 | 「已完成：本次入库 35 篇 / 数据集累计 120 篇。」→（有跳过/失败时加一句「另有 12 篇已存在，已跳过」）→「需要我直接分析这批数据吗？」（只问这一句，不要追加第二句造成重复；用户同意后进入 §10） |
| 单篇完成 | 「这篇笔记已抓取，评论 X 条已入库。」若这篇已存在被跳过（本次入库 0 篇），主动说明并问「要重新抓取更新吗？」 |
| 作者主页完成 | 「已完成：本次入库 35 篇（上限 50 篇）/ 数据集累计 120 篇。」少于上限属正常（作者公开笔记不足或大量已存在被跳过），**不要**因未达上限自动重开；用户追问时才补「可能已无更多公开笔记或已抓过」 |
| 启动确认 | 按下方「启动确认清单」逐项列出，再一句窗口预告与「确认开始？」 |
| 启动成功 | 「我已跟进 3 次，确认已开始抓取，之后你随时可以让我查进度。」+ 一句窗口行为说明（会自动打开、最小化会暂停）。不用报任务 ID，除非用户要 |
| 跟进结束（未完成） | 「任务仍在后台继续，需要时随时让我查进度。」不报字段；不判失败、不新开任务 |
| 暂停 | 「任务已暂停：抓取窗口被最小化。恢复窗口显示后会自动继续，不用重试。」仅当距 10 分钟兜底时限很近时才补时限提醒 |
| 失败 / 中断 | 三段，各一句：① 发生了什么（人话）+ 错误码，如「抓取页被关闭了（`TASK_INTERRUPTED(tab_closed)`）」；② 影响：「已入库 35 篇不受影响，还差 65 篇」；③ 处置：「要我用原条件补抓剩余 65 篇吗？」 |
| 风控拦截 | 「触发小红书验证（`BLOCKED_BY_RISK`），需要你在浏览器里手动完成验证；处理完告诉我，我再重新发起。」 |
| 配额冷却 | 「上一次采集还在冷却，14:35 之后才能开始下一次。」用户追问时才解释「按上次请求量折算，属正常风控保护」 |
| 环境未就绪 | 只报**当前卡住的那一步**：「差一步：请在插件设置 →「AI 接管」中打开总开关。」用户处理完再讲下一步，不要一次列出三步 |
| 离线快照 | 结论在前，新鲜度作括注：「（数据来自上次在线 10:32，可能已变化）」 |
| 离场复盘 | 一句话总结论 →「你不在时：扩展离线过 1 次」→「任务：已完成」→「本次入库 35 篇 / 数据集累计 120 篇」。每条一行，不贴告警原始字段 |

**启动确认清单（固定逐项列出）**

- 目标：关键词「X」／你提供的这篇笔记／这位作者的主页（当前笔记列表）
- 数据集：Y（不存在会自动创建）
- 数量：N 篇／1 篇（单篇固定）
- 跳过已抓取笔记：是（跳过）／否（更新重抓）
- 每篇评论上限：N 条
- 自动展开评论回复：关闭／开启，最多展开 N 次（0=不限；关闭写 —；开启但未指定写「不限」）
- 抓取评论图片：关闭／开启（VIP 专属）
- 抓取节奏：智能／标准

清单后用一句说明独立窗口与最小化暂停，再问「确认开始？」。

**失败场景必须保留错误码**：统一写成「人话 + 括号内错误码」，错误码跟在描述后面，不单独成行、不附带整张释义表。错误码是用户找客服、查文档的唯一凭据，**不得省略**；但机制解释、重试阶梯等分析过程不要上屏。

**反模式（禁止）**

- 把工具响应的原始 JSON、键值对或字段列表直接展示给用户（`extension.connected: true`、`currentArticle: 35`、`lastSeq: 42`、`staleReason: extension-offline`、`processed.articles` 原样列出）；
- 用「字段名：值」的形式「翻译」字段（`currentArticle: 35`）——正确写法是「当前进度：已完成 35 篇」，字段名本身也不能出现；
- 一条回复里同时报进度 + 讲风控原理 + 列错误码含义 + 给多个备选方案；
- 用户只问进度却回一整段复盘报告；或反过来只答「在跑」而不给数字；
- 把内部口径当用户语言（`remaining`、`skipExistingArticles`、`articleLimit`、`targetArticles`），应说「还差 65 篇」「跳过已抓取」「上限 100 篇」「目标 100 篇」。

## 7. VIP 与诚实汇报

- **门禁覆盖范围**：除 `xhs_connection_status`、`xhs_prepare_env` 外，全部工具统一纳入 VIP 门禁（含列表/新建/改名数据集、任务查询/等待/取消/窗口唤醒、三个数据读取工具）。非 VIP 或会员态无法确认时一律返回 `VIP_REQUIRED`。`xhs_prepare_env` 豁免是为了保留冷启动唤醒能力，它不返回业务数据。
- **两条路径不要混读**：Agent 门禁对非 VIP 一律返回 `VIP_REQUIRED`（不启动）；用户在插件里手动发起的抓取由底层防线钳制（笔记数量上限 20、模式锁定标准档、不可抓评论图片），启动响应里的 `effectiveConfig.clamped` / `clampReason` 会如实说明。
- **VIP 过期后的任务控制**：不做「任务归属豁免」——会员态失效后 AI 会失去 `xhs_task_status` / `xhs_task_list` / `xhs_wait_for_task` / `xhs_cancel_task` / `xhs_activate_window` 能力。如实告知用户「请在插件或浏览器中手动取消/恢复窗口」，**不得声称已取消或已恢复任务**。`xhs_connection_status` 仍会返回 `activeTask`，可用来告知用户当前任务概况，但不能据此声称能操作它。已入库数据与任务本身不受影响。
- 被钳制、降级的结果**一律如实转述**，不要按承诺数汇报，也不要承诺插件未达成的数量。
- **articleLimit 是单次任务上限（1-500）**：数据集本身没有数量上限，同一数据集可被多次任务累加（2×500=1000 合法），已有存量不会拒绝新任务。
- **配额口径含手动任务**：任务节奏配额（冷却债 + 24 小时内次数上限 + 风控加成）把用户**在插件里手动发起**的抓取一并计入。被 `QUOTA_EXCEEDED` 拒且原因是次数上限时，如实说明"24 小时内抓取次数已达上限（**含你手动发起的任务**）"，不要暗示是 AI 任务刷满的。
- 汇报入库量用模板句：**「本次入库 X 篇 / 数据集累计 Y 篇」**——「本次产出」与「数据集累计」是两个口径，不要混用（失败后新开任务补抓时尤其如此）；句式按 §6.5「任务完成」模板输出。

## 8. 行为约束

- 不得连续无间隔启动任务（配额为任务节奏冷却债，见 §2.7：按上次任务请求量折算、24 小时内上限 96 次；先查 `xhs_connection_status` 的 `quota` 再启动）。
- 不得绕过 VIP 限制（底层钳制在插件侧强制生效，绕过只会失败）。
- 不得索要或调整风控敏感参数（速度因子等不暴露给 AI）。
- 不得把工具响应原始字段、排查过程或备选方案平铺给用户——输出一律按 §6.5 模板（唯一例外：失败场景必须带上错误码）。

## 9. 能力与字段缺失

- 读取前查看 `xhs_connection_status.extension.capabilities`：`readDatasetMode` / `readCrossDatasetIds` / `readFileOutput` 对应能力为 `false` 或缺失时，提示用户更新插件/本机服务，不改用其它读取方式；不要用错误码反推能力。
- 工具响应中的字段为 `null` 或缺失时，按“当前未提供”处理，不要当成 `false`/`0`，也不要据此宣告异常或数据丢失；`targetArticles` 缺失时 `remaining` 兜底 0，仍不得宣告抓满。

## 10. 数据读取与分析

当用户要「分析/总结/统计已抓取的笔记评论」或「读取数据集内容」时，进入本节。

**前置**：三个数据读取工具恒为 live（无离线快照），扩展离线时先按 §2.8.2 调 `xhs_prepare_env`（豁免 VIP 门禁）唤醒；可用性与新鲜度规则见 §2.8，本节不再复述。

**决策树（漏斗优先，不要跳步盲读）**：

```
分析请求 → 数据集定位（xhs_list_datasets；离线快照边界见 §2.8.1）
  → xhs_connection_status（读 extension.capabilities；缺能力提示更新插件）
  → xhs_dataset_overview（全局认识；标签分布决定是否按标签切片）
  → 用户指定笔记？→ ID 模式 read（仅 articleIds，可跨数据集）
    否则 → 数据集模式 read（仅 datasetId/datasetName + nextCursor 续读）
  → 输出分析结论
```

### 10.1 读取模式与规模

| 条件 | 模式 | 默认参数 |
|---|---|---|
| 用户指定笔记，或 `articleCount ≤ 20` 且 `scrapedCommentCount ≤ 1000` | 一次 ID / 数据集 inline | `commentLimit=100`（要尽量全量时显式 2000，仍可能截断）、`replyLimit=20` |
| 其他情况 | 数据集模式 + 续读 | `maxArticles=50`、`commentLimit=100`、`replyLimit=20`，循环到 `nextCursor=null` |

- **数据集模式**：只传 `datasetId`/`datasetName`，按 `scrapedTime` 倒序、`articleId` 升序返回；`maxArticles` 默认 50（1–100）。
- **ID 模式**：只传 `articleIds`（1–100，可跨数据集）；不要再传 `datasetId`/`datasetName`、`maxArticles`/`cursor`。
- **游标**：`cursor` 只能用于数据集模式，来自上次 `nextCursor`；绑定数据集与读取参数，翻页中途改 `commentLimit` / `commentSort` / `includeReplies` / `replyLimit` 会被拒绝。
- **`commentLimit`**：两种模式默认 100；数据集模式显式 `-1` → `INVALID_ARGS`；ID 模式超过 10 个 ID 时显式 `-1` → `INVALID_ARGS`。要尽量全量时传 2000，超过 2000 条的笔记仍会截断。
- **`replyLimit`**：默认 20；ID 模式超过 10 个 ID 时显式 `0` 且 `includeReplies=true` → `INVALID_ARGS`。≤10 个 ID 时可显式传 0 表示不限回复。
- **批量守卫**：ID 模式超过 10 个时，默认 100/20 是安全值；显式 `commentLimit=-1` 或 `replyLimit=0` 会被拒绝。数据集模式不受此守卫影响（它有自己的默认值）。
- **成本**：`commentLimit` / `replyLimit` 只限制输出，不减少读取、清洗、排序成本；病态大数据集不要靠调小它们“提速”。
- **稳定快照**：需要稳定枚举时先用 `xhs_list_articles(pageSize=1000)` 冻结 ID（超过 1000 篇按 `hasMore` 翻页），但 list 也是时点快照，只能降低漂移。

### 10.2 覆盖度声明

只有以下条件全部满足，才能说“读完了全部评论”：

- `nextCursor=null`；
- `truncatedArticleIds=[]`、`missingArticleIds=[]`；
- `commentsTruncated=false`（且逐篇 `commentsTruncated=false`）；
- `commentsUnavailableArticleIds=[]`；
- `commentLimit` 为 `-1` 或 2000，且没有笔记的顶层评论数超过该值。

否则必须说“覆盖了 N 篇、返回了 M 条评论”，不能把“返回数量”说成“全部”。数据集模式下 `nextCursor` 非空时继续用 cursor，不要按 `truncatedArticleIds` 重读；ID 模式才用 `truncatedArticleIds` 判断是否缩小 `articleIds`。

### 10.3 两遍法（可选，明确是抽样）

1. 第一遍：`commentLimit=0` 读正文（按 `maxArticles` 分批），建立主题/结构认识；
2. 第二遍：按 `xhs_dataset_overview` 的 Top5 或 `xhs_list_articles(sort=likeCount/commentCount)` 选 10–20 篇读评论；
3. 告诉用户“第二遍是热度抽样，不代表全部评论”；
4. 需要全量统计时走后续聚合能力或更多分批，不要把抽样说成全量。

### 10.4 读取纪律与口径

读取前按 §9 确认能力；能力不可用时提示更新，不改用其它读取方式。

1. **漏斗优先**：禁止跳过 overview/list 对大数据集盲读；「分析整个数据集」＝ overview 结论 + 代表性笔记抽样（热门榜优先），不是全量读取。
2. **规模自律**：读取前先按 §10.1 选模式；`scrapedComments` 含回复，`commentLimit` 只按**顶层评论**计，两者不是同一口径；只统计**最终有效**的顶层评论，被清洗消除的评论不占名额、会按 `commentSort` 向后补位。评论 >500 时先与用户确认口径（全量 / 热评取样）。收到 `truncated=true` 时：数据集模式看 `returnedArticles` 与 `nextCursor`（继续用 cursor，不按 ID 重读）；ID 模式看 `returnedTopLevel` 与目标，未达目标降 `articleIds`/`commentLimit`，已达目标但仍有大评论被跳过或回复被截断时，降 `replyLimit` 重读该篇，不硬塞。
3. **限流纪律**：连续读取注意操作频控（`RATE_LIMITED`），失败后 ≥10 秒再试，不紧密重试。
4. **口径与清洗转译**（字段名不上屏）：
   - 双口径：「这篇笔记显示 210 条评论，实际抓取了 180 条」（实际抓取数含回复）；overview 的 `interactions.totalComments` 是页面显示总数，`dataset.scrapedCommentCount` 是已抓数。
   - 清洗：「已应用内置清洗（全篇文章的表情/图片占位、@提及、特殊符号、无意义内容）」；用户规则开启时补「全篇额外过滤 N 条」；本次返回 M 条顶层（R 条回复）。不要把全篇清洗统计与本次返回条数相加或混用。`cleared` 是清洗口径，可能包含读取层未返回的评论（如 `includeReplies=false` 时主评被清空且无回复的评论整条消失）。
   - 规则 1-4 对 AI 读取恒开；不要对用户说「未配置清洗规则」或「数据可能含表情、水评」。
   - `activeCrawl=true`：「该数据集仍在抓取中，以下数据是当前时点的快照」；overview/list/read 都可能返回该标志，手工任务同样适用。
   - 标签：`tagNamesNotFound` 非空时如实说明哪些标签不存在，不要把空结果当成数据集没有内容。
   - 分页：read 数据集模式看 `totalArticles` / `returnedArticles` / `nextCursor`；list 看 `total` / `hasMore`，不要靠空页猜结束。
   - 统计口径：`cleaning.statsScope="returned"` 表示 `cleaning.stats` 只聚合本页返回篇目，不是数据集全量。
   - 缺失文章：ID 模式表示内部 id 不存在；数据集模式表示扫描后读取缺失的竞态。`truncatedArticleIds` 在 ID 模式表示因预算未返回；在数据集模式只表示单篇过大被跳过、cursor 已越过，其余未返回篇目由 `nextCursor` 表达。
   - ID 模式：`dataset=null`、`datasets` 非空、每篇带 `datasetId`；`articleIds` 是插件内部 id，不是小红书 note id，同一笔记跨数据集可能是两个不同 id。
   - `commentsTruncated`（逐篇）表示该篇有评论因预算被跳过或回复被截断。
   - 读取失败：`commentsUnavailableArticleIds` 非空（或某篇 `commentsUnavailable=true`）时，不得说「这篇没有评论」，应说明「评论读取失败」，并建议用更小的 `articleIds` 重试；这类文章 `returnedTopLevel=0` 且没有 `cleaningStats`。
5. **结论不贴数据**：读取是手段，给用户的是分析结论；禁止把渲染后的 markdown 原文大段回显（§6.5 反模式沿用）。

**VIP 门禁与过期后的任务控制**见 §7。

**采集完成后的衔接**：按 §6.5「任务完成」模板询问是否直接分析；用户同意后从本节漏斗第一步开始，不重复询问。

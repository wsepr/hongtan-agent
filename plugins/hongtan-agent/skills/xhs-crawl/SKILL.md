# 红探小红书评论采集工作流

红探是一个小红书评论采集插件（Chrome 扩展）。你通过 MCP 工具控制它：启动/停止抓取、查询任务状态、管理数据集。

**任务的存续不依赖你是否在线。** 任务是一次不可复活的执行：中断即终态失败，继续抓取只能新开任务（§2.6），你是指挥官与播报员。

## 1. 触发与边界

- **触发**：请求实质涉及「采集／抓取小红书评论」「找客户数据」「把某个关键词的笔记评论存下来」时，默认进入本工作流，即使用户没有点名红探。
- **不触发**：普通寒暄；与小红书评论采集无关的任务；用户明确说「不要用红探／不要调用工具／只用我提供的材料」。

## 2. 工具选用决策树

严格按以下顺序执行，不要跳步：

1. **`xhs_connection_status`** —— 先确认链路就绪。读取：
   - `extension.connected`（扩展是否已连上本机服务）
   - `extension.agentEnabled` / `extension.deviceApproved`（开关与设备批准）
   - `vip.isVip` 与 `vip.effectiveArticleLimit`（会员态与本次可用篇数上限）
   - `quota`（任务节奏配额快照；`readyAt` 非空 = 需等到该时刻才能启动——先告知用户并等待，**不要试跑**，见 §2.7）
   - `lastKnown`（**离线时**的上次在线会话摘要：`lastSeenAt` / `vip` / `quota` / `extId` / `browserFamily` / `cachedAt`；在线时为 `null`）
   - `canWake`（是否可调 `xhs_prepare_env` 唤醒环境）、`alerts`（最近告警摘要，**仅覆盖当前本机服务进程存活期**）
   - `onboarding`（未就绪时的具体指引）

   **意图分流（先分再动，不要一律先拉起浏览器）**：
   - **只读 + 有快照** → 直接答，标注新鲜度（见 §2.8）；
   - **只读 + 要准确/无快照** → `xhs_prepare_env`（轻确认）后再读；
   - **要抓取** → 直接 `xhs_start_crawl`（它自带拉起），**不要先 prepare**——先 prepare 只会多一次弹窗与一轮等待。
2. **互斥检查**：若 `activeTask` 非空，先用 `xhs_task_status` 查看它，不要再启动新任务（否则会得到 `TASK_BUSY`）。
3. **数据集**：用 `xhs_list_datasets` 查看现有数据集；需要新建时用 `xhs_create_dataset`（按名幂等，重名不报错）。也可以在 `xhs_start_crawl` 里直接传 `datasetName` —— 不存在会自动创建。
4. **`xhs_start_crawl`** —— 启动抓取，立即返回 `taskId`（**不会等待完成**）。
   - **config 可选参数**（与插件配置界面同源，用户有偏好时按其偏好传入并在确认时复述）：
     - `skipExistingArticles`：跳过数据集中已存在的笔记，**默认 true**——增量/补抓场景保持默认；用户明确要全量重抓（更新已有笔记）时传 false；
     - `autoExpandCommentReplies`：自动展开评论中的回复内容，**默认 false**——用户要求抓完整回复楼/楼中楼时传 true；
     - `commentExpandLimit`：每条评论最多展开次数（0-999，0=不限），仅当 `autoExpandCommentReplies=true` 时生效；
     - 另有 `commentLimit`（每篇评论上限，默认 100）、`crawlMode`（默认 smart）、`crawlCommentImages`（VIP 专属，默认 false）。
   - 速度因子等风控敏感参数不暴露（见 §8），不要索要或猜测。
5. **汇报 task handle**，转入监控。

## 2.5 接入引导（onboarding 分流：自动拉起 vs 人工）

`xhs_connection_status` 返回的 `extension` 三态字段决定走自动还是人工——**先分流再行动**，不要把「断连」一律当成需要人工：

- **自动路径**：`extension.connected === false` 且 `agentEnabled` / `deviceApproved` 均为 `null`（浏览器多半没开）→ **不必等用户回话**，直接进决策树第 4 步调 `xhs_start_crawl`，本机服务会自动拉起浏览器并等待扩展连接；仅当返回 `EXTENSION_UNAVAILABLE`（首次引导：扩展从未连接过、本机无从解析浏览器配置）才转人工路径。
- **人工路径**（浏览器开着但未就绪，按下表对号入座，不要自己发明步骤）：

| 步骤 | 判据 | 你要用户做的事 |
|---|---|---|
| ① 开关就绪 | `extension.agentEnabled === false` | 请用户在插件设置 →「Agent 接管」中打开总开关 |
| ② 设备批准 | `extension.deviceApproved === false` | 请用户在插件设置 →「Agent 接管」→ 设备管理中核对本机指纹并点击批准（`pairing.fingerprint` 可复述给用户核对） |
| ③ 会员态 | ①② 就绪但 `vip.isVip === false` | 如实说明「AI 联动为 VIP 功能」，引导开通会员或登录红探账号 |

人工路径**每一步都等用户回话后再复查**，不要连续调用工具空转；全绿后才进入工具选用决策树的第 3 步。

## 2.6 任务失败后的重试（v3：任务不可复活，无续跑）

任务只有一种**中间态**：`stalled_by_background`（抓取窗口被遮挡或最小化，恢复窗口可见后自动继续；超过 10 分钟未恢复会终态失败）。风控与一切运行中断都是**终态 `failed`**，不存在自动恢复，也不存在续跑参数：

- `TASK_INTERRUPTED`（`error.reason` 归因：`tab_closed`=抓取标签页已关闭 / `page_left`=页面已离开小红书 / `heartbeat_timeout`=心跳超时 / `browser_gone`=浏览器已重启 / `stalled_timeout`=窗口长时间不可见）：任务已终态失败；
- `BLOCKED_BY_RISK`：触发风控/验证码，任务已终态失败。

**标准重试流程**（读到 `failed` 时）：

1. 用 `xhs_task_status` 读快照的 `processed.articles` 与 `remaining`（= max(0, `articleLimit` − 已抓篇数)）；
2. `remaining === 0` → 告知用户「本任务已抓满目标数，已入库的数据不受影响」，**不重开**；
3. `remaining > 0` → **征得用户同意后**用**原参数新开任务**：同 keyword/noteUrl 与 datasetName，`articleLimit = remaining`，`skipExistingArticles = true`（不重复入库），其余 config 沿用；新任务是全新 taskId，走完整启动流程（含确认协议 §3 与配额 §2.7）；
4. 被 `QUOTA_EXCEEDED` 拒绝 → 如实转述可重试时刻，**不换参硬试**；
5. 同一任务因基础设施中断（浏览器退出、页面被关等），**最多建议用户重试一次**——反复中断说明环境有问题，应先排查而不是循环重开。

旧参数 `resumeTaskId` 已下线：传入会返回 `INVALID_ARGS`（消息会给出新开任务的参数指引），不要使用。

## 2.7 任务配额（冷却债）

红探对「新任务启动」有节奏配额：**按上次任务实际采集的请求量折算冷却时间**（不是固定间隔）——轻任务几十秒、重任务至多 10 分钟；24 小时内最多 96 次。同一账号短时间内连续大量请求会触发小红书风控，采集得越多、冷却越久，属正常保护。

处理规则：

- **启动前先看** `xhs_connection_status` 的 `quota`：`readyAt` 非空时**不要调 `xhs_start_crawl` 试跑**（必被拒），直接把可启动时刻告诉用户（如「上一次采集后需要冷却到 14:35 才能开始下一次」），到时间再走决策树。`readyAt` 为 null（且键存在）= 现在可启动。
- **若响应里没有 `quota` 键**：说明运行中的服务进程旧于当前契约（quota 能力尚不存在）。**停止试跑**，不要把缺键当「可启动」；向用户说明运行时需要更新——结束该服务进程后，下一次工具调用会自动重拉新版本。
- **被拒时**（`QUOTA_EXCEEDED`，消息里带原因与可重试时刻）：如实转述时刻；**不要反复试跑、不要改参数/换数据集重试、不要当成插件故障或宣告失败**。
- 用户想「尽快开始」时：唯一正确路径是等到 `readyAt`（或把多个目标合并进之后的一次任务里）；不要寻找任何绕过方式。

## 2.8 只读场景：快照读取与 `xhs_prepare_env` 唤醒

### 2.8.1 离线快照（不弹窗就能答）

`xhs_list_datasets` 在扩展离线且**上次在线快照未过期**（24 小时内）时返回 `source: "cache"` + `stale: true` + `cachedAt`。此时：

- **如实复述**："这是上次浏览器在线时（`cachedAt`）看到的列表，可能已过期"；不得把快照当实时数据；
- 快照**只用于给用户看与选**：不参与存在性判断、不用于容量校验；写入路径仍由插件按名权威解析（重名幂等/不存在则建）；
- 用户确认后又需要准确值时，按 §2.8.2 唤醒后重查；
- 返回 `EXTENSION_OFFLINE`（无快照 / 快照超 24 小时 / 换过浏览器）时，说明"没有可用的上次快照"，按 §2.8.2 或 §2.5 处理。

`xhs_task_status` / `xhs_task_list` 不做缓存，但响应带 `freshness`（`extensionConnected` / `lastExtensionMessageAt` / `staleReason`）：

- `staleReason: "extension-offline"` = 账本停在最后一次上报，**不得当成实时**；
- 账本里有活跃任务且扩展离线时，工具会自动尝试重新拉起浏览器（响应带 `repair`），此时按 §4 的间隔复查，不要自己再试跑。

### 2.8.2 `xhs_prepare_env`：只读意图的唤醒

- 语义：**纯唤醒**（拉起浏览器并等扩展连接），**不返回数据集、不占任务单飞、不消耗任务节奏配额、不建抓取任务**；已连上时立即返回、不做任何动作；
- 返回 `ensure.state`：`connected`（可用）/ `connecting`（已发起，等 ≥10 秒复查 `xhs_connection_status`）/ `needs_manual_open`（首次引导：扩展从未连接过、本机无从解析浏览器 → 按 §5 的 `BROWSER_UNRESOLVABLE` 阶梯引导用户手动打开）；
- 入参 `waitSec` 建议不传或传小值（默认立即返回）；**单次调用不超过 30 秒**；
- **确认强度（轻量）**：调用前一句话说明"需要打开浏览器，约 10-60 秒，会把窗口切到前台"，获同意即可——不必复述抓取参数；用户已在推进抓取工作流（明确说要抓/要选集）时可直接调用。

## 3. 确认协议（启动前必做）

启动之前必须向用户复述并获确认：

- 目标（关键词或笔记链接）
- 数据集名
- 数量上限（`articleLimit`）

若用户明确表达了「跳过已抓取/增量抓取」「展开回复楼」等偏好，将其映射为对应的 `config` 参数（§2 第 4 步）并在复述时一并说明；未表达时使用默认值，不必逐项追问。

同时必须告知这两件事，缺一不可：

- 该操作会**打开一个独立的抓取窗口**（不占用用户当前的页面），本机在启动时会**尝试**把它**带到前台**（失败不阻塞任务）；该窗口**不会被自动关闭**（成功/失败/暂停都一样），留作排查现场，用户可自行关闭；
- 采集期间**若该窗口被最小化，任务会暂停**（恢复窗口可见后自动继续）；**被别的窗口盖住不再导致停摆**（由本机服务冷启动的浏览器已带消遮挡开关）。不必要求用户「保持前台、勿遮挡」——最小化只会暂停，不会失败，也不需要重试。

另需预告一种现象，避免用户把闪退当独立故障：若用户自行关闭抓取窗口、而那是浏览器里唯一的窗口，**浏览器会一起退出**——这是预期行为，不要把它当成新故障。

**离场提示（用户要离开一段时间时一并说明）**：别关闭浏览器（关掉＝任务中断且插件无法自愈）、别让电脑睡眠或熄屏、风控卡住只能等他回来处理；长跑优先建议用户**手动打开**浏览器（不受宿主进程回收影响，见 §5）。

## 4. 监控约定

任务启动后是**异步自持**的，你的等待方式必须是「多次短挂起 + 游标续读」，而不是一次长等：

- **标准用法**：循环调用 `xhs_wait_for_task`，**不传 `timeoutSec`（使用默认）**；把上一次返回的 `lastSeq` 原样作为下一次的 `sinceSeq` 续读增量进度。每次返回后检查 `snapshot.state` / `timedOut`，未到终态就再挂起一次。
- **即使契约允许更大的 `timeoutSec`，每次挂起也不得超过 30 秒**——宿主对单次工具调用有约 60 秒的硬性放弃线，长挂起必然以传输层错误收场。
- **三条禁令**：
  1. 不传 `timeoutSec > 30`；
  2. `MCP error -32603` 之类传输层错误**不是业务失败**——它只说明宿主放弃了这次调用，任务可能仍在推进；收到后**禁止重发任何等待类调用**（`xhs_wait_for_task` / `xhs_cancel_task`），一律降级为 `xhs_task_status` 快照确认现场；
  3. 响应里 `timedOut: true` 才是「本轮等待到期」的业务语义，可以继续下一轮短挂起。
- **轮询间隔不得少于 10 秒。** 禁止紧密轮询占住会话。
- 若 `xhs_task_status` 返回 **`orphaned: true`**（活跃任务超过 60 秒没有新消息）：先看 `state` 再解读——**`running` 时**这是"上报侧暂时失联"，插件会自行收敛为终态（如实转述「任务暂时失联，插件即将给出终态结论」，**不要宣告失败、不要重试、也不要另起一个任务**，按 ≥10 秒间隔复查）；**`stalled_by_background` 时**它只表示"账本停止更新"（遮挡即冻结，恢复可见自动继续，超 10 分钟插件会终态化），**不要**把它说成故障。
- 用户几小时后才回来问一句时：直接 `xhs_task_status` 看快照（任务在浏览器里自持运行），或用 `xhs_task_list` 复盘「我不在的时候发生了什么」。

### 4.1 用户离开后回来：标准复盘顺序

1. **告警摘要**：先看 `xhs_connection_status` 的 `alerts`（`kind` / `at` / `taskId`），据此说明"你不在时发生了什么"（如扩展离线过 10 分钟、任务心跳停滞过 5 分钟）。**边界**：该摘要只覆盖**当前本机服务进程存活期**，更早的要看本机服务日志，不要声称覆盖全部历史；
2. **任务现状**：`xhs_task_list`（含 `source` 区分 AI / 手动）→ 对其中活跃或中间态的任务看 `freshness` 与快照状态，如实转述（冻结的账本不得当实时）；
3. **入库口径**：`xhs_list_datasets` 取"数据集累计"；**「本次入库 X 篇 / 数据集累计 Y 篇」两个口径不得混用**；离线时用快照并复述 `cachedAt`。

## 5. 失败排查映射（逐条）

| 错误码 | 你应当做的 |
|---|---|
| `AGENT_DISABLED` | 提示用户在红探插件设置 →「Agent 接管」中开启；**不重试** |
| `DEVICE_NOT_APPROVED` | 提示用户在插件设置 →「Agent 接管」→ 设备管理中核对指纹并批准 |
| `EXTENSION_OFFLINE` | 说明「采集扩展暂时休眠，稍后即可恢复」；**禁止紧密重试**，稍后（≥10 秒）再查 |
| `EXTENSION_UNAVAILABLE` | 说明扩展可能未安装、被禁用或权限被撤销，提示用户检查 `chrome://extensions` |
| `BROWSER_UNRESOLVABLE` | 本机服务解析不出要拉起的浏览器。按下方「诊断、尝试拉起与引导」阶梯逐级处理：只读定位 → 经宿主 shell 尝试启动并**验证扩展已连上** → 仍失败才请用户手动打开 |
| `PROTOCOL_VERSION_MISMATCH` | 提示升级红探插件或红探 Agent 运行时 |
| `VIP_REQUIRED` | 如实说明「AI 联动为 VIP 功能」，引导开通会员或登录红探账号；**不重试** |
| `NOT_LOGGED_IN` | 提示用户在浏览器中登录小红书后重试 |
| `LOGIN_WALL` | 现象是「页面能打开但结果列表为空」。提示用户登录小红书后重试 |
| `CONTENT_NOT_READY` | 说明页面类型可能不符或被重定向；**最多允许重试一次** |
| `URL_NOT_MATCHED` | 说明该 URL 不支持（仅支持搜索结果页 / 笔记详情页 / 用户主页） |
| `TAB_UNAVAILABLE` | 抓取标签页已关闭或不可用，任务已终态失败（不自动恢复）；按 `TASK_INTERRUPTED` 的重试流程处理（§2.6） |
| `TASK_BUSY` | 先用 `xhs_task_status` 查询当前任务，勿盲目启动。**看来源**：`source:"manual"` 表示占用者是**用户手动发起**的任务 —— 如实说明"插件里有一个手动任务在跑（数据集「X」），请等它完成或在插件中结束"，**不要**去取消它（见下 `CANCEL_REJECTED`） |
| `CANCEL_TIMEOUT` / `CANCEL_REJECTED` | 说明抓取可能仍在进行，稍后复查。**`CANCEL_REJECTED` 若原因是手工任务**（`source:"manual"`）：说明"手工任务请在插件中取消"，**不得声称已取消** |
| `BLOCKED_BY_RISK` | 任务已终态失败（风控/验证码不会自动解除后复活任务）。提示用户在浏览器中完成验证；用户确认处理后按 §2.6 标准重试流程征得同意再新开任务；**禁止自动重试** |
| `STALLED_BY_BACKGROUND` | 转述「抓取窗口被最小化，任务已暂停，恢复窗口可见后自动继续」；**不要重试、不要判失败**，也不要要求用户保持前台。**被别的窗口盖住不再导致停摆**（本机服务冷启动的浏览器带消遮挡开关）——若用户报告"只是被挡住"，先查快照时间戳，别把旧样本当实时。用户在场且希望立即恢复时，**先征询**再调 `xhs_activate_window`（会抢焦点；前台化由本机服务用 OS 级方式执行，`activated=false` 时按 `reason` 说明原因并请用户点击任务栏中闪烁的窗口，**不要反复重试**）。注意：暂停超 10 分钟未恢复，插件会把任务终态化为 `failed/TASK_INTERRUPTED(stalled_timeout)`，届时按 §2.6 处理 |
| `QUOTA_EXCEEDED` | 说明配额冷却中（按上次任务请求量折算，见 §2.7），消息里会给可重试时刻；**不要连续试跑、不要换参数/数据集重试**，到时间再按用户要求启动 |
| `TASK_INTERRUPTED` | 任务被中断且已终态失败（`error.reason` 给出结构化归因），按 §2.6 标准重试流程处理：读 `remaining`，为 0 告知已完成不重开，>0 征得同意后原参数新开任务；同一任务最多建议重试一次 |
| `RATE_LIMITED` | 说明操作过频，稍后重试 |
| `TASK_NOT_FOUND` | 核对 `taskId` 是否来自 `xhs_start_crawl` 的返回；任务超过 24 小时会被账本清理 |
| `INVALID_ARGS` | 按工具 `inputSchema` 修正参数后重试（特别注意 `articleLimit` 必填、1-500） |
| `UNKNOWN_TOOL` | 说明工具集可能需升级运行时；用 `xhs_connection_status` 查看当前可用能力 |
| `BROKER_NO_RESPONSE` | 请求已送达但结果未知——**先调 `xhs_task_status` 确认是否已生效，禁止直接重发**等待/启动类调用 |
| `RUNTIME_STALE` | 运行进程旧于当前契约——按消息里的 pid 结束该进程，下一次工具调用会自动重拉新版本；不要反复重试 |
| `BROKER_ERROR` | Broker 内部执行异常——启动/等待/取消类调用可能已部分生效，先 `xhs_task_status` 确认现场再决定是否重试；持续出现说明运行时异常 |
| `BROKER_UNREACHABLE` | Broker 未运行且自动拉起失败——提示用户手动启动红探 Agent 服务后再试；不要紧密重试 |

**`BROWSER_UNRESOLVABLE` 的诊断、尝试拉起与引导（阶梯式，逐级退守，不要跳级）**：

该错误表示 Broker 解析不出浏览器可执行文件（便携安装、非标准位置、系统探测失败），自动拉起已不可能。但 **AI 侧仍可尝试自救**——定位与启动方式**按当前操作系统的惯例自行选择**，前提是每一步都验证，不把「启动成功」当「环境可靠」：

1. **只读定位**：用当前 OS 的常规机制定位已安装的浏览器（Windows：注册表 App Paths、Program Files 常见目录；macOS：/Applications；Linux：PATH 与常见 bin 目录）。完全找不到 → 跳到第 3 步。
2. **经宿主 shell 尝试启动 + 验证存活**：
   - **不要在沙盒 shell 中启动**（实证：WorkBuddy 在沙盒中启动的浏览器随沙盒/会话销毁而死亡）——宿主提供非沙盒 shell 时，用**非沙盒模式**执行；只有沙盒 shell 可用 → 跳过本步直接进第 3 步；
   - 启动用当前 OS 的**脱离式惯用法**（不阻塞当前命令、启动的浏览器进程与宿主 shell 解耦），可直接启动浏览器或打开任务深链 URL；
   - 启动后**必须先验证再重发任务**：等 5~10 秒调 `xhs_connection_status`，`extension.connected === true` 才重新走 `xhs_start_crawl`（原任务已终态，需新建；数据集口径不变）；
   - 未连上或连上后掉线 → 该宿主会回收派生进程，退回第 3 步。
   - **已知风险，必须向用户说明**：验证通过只代表当下存活——宿主差异存在（沙盒派生进程会随沙盒销毁；非沙盒启动已实测可存活）。无人值守长跑场景，优先建议用户手动打开浏览器（用户手动开的浏览器不受宿主回收影响）。
3. **引导用户手动打开**：告知浏览器位置（第 1 步结果）并请其手动打开（用户手动启动的进程不受宿主回收影响，是最可靠路径）；打开后扩展自动连上本机服务，恢复正常流程。

**表中没有的码**（含形态不明的 `MCP error -32603` 等传输层错误）：⇒ **原样转述给用户、不重试、不推测原因**；若该调用有副作用（启动/等待/取消），先 `xhs_task_status` 查看是否已生效再决定下一步。

**账本内部码**（不在契约 `errorCodes` 表内，但会出现在任务快照的 `error` 里，按上一条原样转述并补一句解读）：
- `BROKER_RESTARTED`：本机服务重启导致账本占位失败；插件重连后会以它上报的真实状态为准，**不要据此判定任务已死**；
- `TASK_STALE`：任务超过 24 小时未终态被账本清理；
- `SUPERSEDED`：同一标签页发起了新的手动抓取，旧任务被顶替取消。

**两条「不得重试，也不得宣告失败」**：`EXTENSION_OFFLINE`、`STALLED_BY_BACKGROUND`。
**一条「必须人工」**：`BLOCKED_BY_RISK`。

## 6. 自我边界（无人值守前提）

- 你不在线时任务照常运行；但**任务不可复活**——中断（页面被关/浏览器退出/风控）一律终态失败，插件不会自动恢复，继续抓取的唯一方式是按 §2.6 新开任务。
- 因此你**不应**把「需要重试」当作己任，也**不应**因一次工具调用失败或连接断开就宣告任务失败；同理也**不应**在未经用户确认时自动重开失败任务。
- 已入库的数据不会丢失：新开任务带 `skipExistingArticles=true`，按 `remaining` 补抓，不会重复入库。

## 7. VIP 与诚实汇报

- **两条路径不要混读**：Agent 门禁对非 VIP 一律返回 `VIP_REQUIRED`（不启动）；用户在插件里手动发起的抓取由底层防线钳制（笔记数量上限 20、模式锁定标准档、不可抓评论图片），启动响应里的 `effectiveConfig.clamped` / `clampReason` 会如实说明。
- 被钳制、降级的结果**一律如实转述**，不要按承诺数汇报，也不要承诺插件未达成的数量。
- **articleLimit 是单次任务上限（1-500）**：数据集本身没有数量上限，同一数据集可被多次任务累加（2×500=1000 合法），已有存量不会拒绝新任务。
- **配额口径含手动任务**：任务节奏配额（冷却债 + 24 小时内次数上限 + 风控加成）把用户**在插件里手动发起**的抓取一并计入。被 `QUOTA_EXCEEDED` 拒且原因是次数上限时，如实说明"24 小时内抓取次数已达上限（**含你手动发起的任务**）"，不要暗示是 AI 任务刷满的。
- 汇报入库量用模板句：**「本次入库 X 篇 / 数据集累计 Y 篇」**——「本次产出」与「数据集累计」是两个口径，不要混用（失败后新开任务补抓时尤其如此）。

## 8. 行为约束

- 不得连续无间隔启动任务（配额为任务节奏冷却债，见 §2.7：按上次任务请求量折算、24 小时内上限 96 次；先查 `xhs_connection_status` 的 `quota` 再启动）。
- 不得绕过 VIP 限制（底层钳制在插件侧强制生效，绕过只会失败）。
- 不得索要或调整风控敏感参数（速度因子等不暴露给 AI）。

## 9. 版本对齐

本 Skill 与 `contracts/xhs-agent-tools-v1.json` 同级管理，版本号与 `toolsVersion` 联动（当前 `toolsVersion: 11`、`protocolVersion: 2`）。工具响应中的快照字段为 `null` 时表示**运行中的插件/服务版本较旧、尚无该字段**，不代表对应能力或窗口不存在——按旧运行时处置，不要把 null 解读成异常。
